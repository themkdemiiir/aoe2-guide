# replay-rs — fast in-process AoE2 replay pipeline

A Rust port of the validated Python pipeline in `../replays/`. It downloads
AoE2: DE replays (signed Azure blobs from the World's Edge Link API) and parses
them **in-process** with the [`aoe2rec`](https://github.com/aoe2ct/aoe2rec)
library — no subprocess, no JSON roundtrip — fanning download+parse across cores
with rayon. The Python version stays as the reference/fallback; this is the fast
path for bulk processing.

It produces the same four tables, with identical semantics (verified byte-for-byte
against the Python `extract.extract` on the same replay):

| table     | shape                                                                   |
|-----------|-------------------------------------------------------------------------|
| `meta`    | one row: match_id, build, version_major, map_id, duration_ms, n_players |
| `players` | one per real player: profile_id, civ_id, name, team, color, won         |
| `events`  | **every** action (full timeline, nothing dropped)                       |
| `ages`    | per player per age reached: uptime + cumulative composition             |

Output is **gzipped** newline-delimited JSON (`*.ndjson.gz`) under `--out`; DuckDB
reads `.gz` natively via `read_json_auto`. (Parquet/arrow are intentionally avoided
— too heavy.) Gzip is essential at scale: the events table dominates and the full
411k-match corpus would be ~100GB+ raw — gzip cuts the event stream roughly 10x.

**Robustness:** each replay's parse runs inside `catch_unwind`. A rare corrupt
replay makes aoe2rec panic (e.g. a `capacity overflow` from a garbage length) or
return `Err`; either way that one match becomes a terminal `parse_failed` (message
recorded in the manifest) and the run continues — one bad replay never crashes the
batch.

## Setup (one-time)

The replay parser is **vendored, not committed** (see the repo `.gitignore`). Clone
it once before building:

```sh
git clone https://github.com/aoe2ct/aoe2rec \
  scripts/data-pipeline/replay-rs/vendor/aoe2rec
```

## Build

```sh
cd scripts/data-pipeline/replay-rs
cargo build --release          # ~50s clean on 16 cores; binary at target/release/replay-rs
```

No edits to the vendored parser are needed — every field the extractor reads is
already `pub`.

## Run

```sh
# 1. seed the manifest with match_ids (newline list OR csv with match_id[,ladder,played_at])
./target/release/replay-rs seed ids.csv --db manifest.sqlite

# 2. process: getReplayFiles (rate-limited) -> parallel download+parse -> *.ndjson.gz shards
./target/release/replay-rs run \
  --db manifest.sqlite \
  --out shards \
  --threads 12 \
  --limit 1000          # optional cap; omit to drain all pending

# parse-only throughput benchmark over a dir of raw .aoe2record files
./target/release/replay-rs bench ./some-replays --threads 16 --repeat 40
```

Fully **resumable + idempotent**: every match ends in exactly one terminal status
(`parsed` / `no_replay` / `expired` / `parse_failed` / `error`) recorded in the
SQLite manifest (WAL). Re-running picks up only what's still `pending` (or retries
the transient `error` status if re-seeded). `error` is retryable; the others are
terminal.

## Analyze (post-game coaching)

`analyze` turns one replay into a per-player macro-coaching scorecard + prioritized
"top fixes". It reuses the parser but is otherwise independent of the bulk pipeline.

```sh
# a local save (the recording player is auto-detected as "you")
./target/release/replay-rs analyze "/path/to/MP Replay ….aoe2record"

# or download by match id (getReplayFiles -> download -> parse); --you overrides "you"
./target/release/replay-rs analyze --match-id 475242532 --you MKD
```

It reports age-up times, villagers@Castle, idle-TC, APM, ELO (read straight from the
replay's PostGame leaderboard — 1v1 ladder 3 / team ladder 4), win/loss (team-aware),
a flank/pocket **role** tag (color/slot rule, only on `open`/`closed` maps — see
`data/maps.tsv`), **scouting** (when you first reached the enemy) + enemy proximity,
an **estimated** resource-float signal, and findings vs your-ELO benchmark / opponent /
absolute-waste thresholds. It is a **macro coach** — no fights, micro, map control, or
exact resources (stated in the report footer).

**Committed data** (all under `data/`, regenerated by `scripts/data-pipeline/`):
- `maps.tsv` — map id → name → **family** → notes. Edit the `family` column
  (`open`/`closed` get the role tag; `hybrid`/`water`/`nomad`/`special`/`other` don't).
  Families were classified from the AoE2 Fandom wiki by real flank/pocket structure.
- `civs.tsv` — civ id → slug (benchmark key). From `src/data/civ-id-map.json`.
- `costs.json` — unit/building/tech costs for the float estimator. Regenerate:
  `node scripts/data-pipeline/build-costs.mjs` (reads `.cache/aoe2-data/data.json`).
- `benchmark.json` — age-up median timings per civ. **v1 is an all-ELO placeholder**
  (`_partial: true`) from `match_ages.parquet`; regenerate the full
  civ×elo_bucket×(1v1|team) version with `build-benchmark.sql` + `build-benchmark.mjs`
  on the VM when the DuckDB is unlocked. Villager medians are deferred (the historical
  per-age basis differs from the analyzer's cumulative count).

## Layout

| file          | responsibility (Python counterpart)                          |
|---------------|--------------------------------------------------------------|
| `config.rs`   | constants, AoE2 ids, status vocabulary (`config.py`)         |
| `manifest.rs` | resumable SQLite ledger (`manifest.py`)                      |
| `api.rs`      | getReplayFiles client, rate limiter, blob download (`api.py`)|
| `extract.rs`  | the semantic extraction — the core port (`extract.py`)       |
| `store.rs`    | gzipped NDJSON shard writers (`store.py`'s parquet writer)   |
| `pipeline.rs` | orchestrator: batch → rayon download+parse → store (`pipeline.py`) |
| `seed.rs`     | seed-file (csv/newline) parsing                              |
| `main.rs`     | CLI: `seed` / `run` / `bench`                                |
